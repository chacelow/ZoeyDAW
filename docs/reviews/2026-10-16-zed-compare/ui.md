# UI 组件系统、主题、布局与渲染性能对比

## 范围与结论

比较的是仓库内固定版本的 Zed，以及当前 gpuix 应用和它使用的 React/native 桥接层。全程只读源码，未启动应用、运行测试或测量帧率。因此，下文的性能影响与实施代价均为 `[INFERENCE]`，不代表已经测得 Zed 比我们快。

最值得学的是把已有能力做成可复用、可发现、可观测的应用接口，而不是重写为 Rust。我们已有完整主题 token、43 套配色、Gallery、quad-batch、局部订阅和性能 runner。尤其需要纠正两个容易误判的点：gpuix 已有 `<virtual-list>`，不能说缺少底层列表虚拟化；minimap 已隔离播放更新，但并未把所有 Clip 绘制虚拟化或批量化。

证据入口：主题 `apps/gpuix/src/shared/theme/README.md:20-42`；列表 `.gpuix-main/packages/react/src/components/index.ts:117-121`；minimap `apps/gpuix/src/project/sections/arrangement/timeline/minimap/Overview.tsx:8-56` 与 `render-cost.test.tsx:141-162`。

## 我们做得不差或更好

- **设计 token 的职责与覆盖测试已经扎实。** shape、Card inset owner、number font 和业务几何分开，不需要为了学 Zed 推倒重建。证据 `apps/gpuix/src/shared/theme/README.md:20-28`。43 预设 × 明暗的派生色和亮度不变量有明确约定，证据同文件 `101-105`；预设派生在模块初始化完成，证据 `presets.ts:20-27`。Zed 也有主题数据/refinement，证据 `.gpuix-main/zed/crates/theme_settings/src/schema.rs:24-38,65-103`。这里只判断我们不缺这层结构，不宣称两者的测试结果胜负。
- **minimap 已经把高频播放更新与重内容分开。** `Overview` 使用 memo，且只订阅 tracks/markers，证据 `apps/gpuix/src/project/sections/arrangement/timeline/minimap/Overview.tsx:8-20`。测试在 16 与 1024 Clip 场景断言播放移动及 viewport 改变不会读取未变 Clip 几何，证据 `render-cost.test.tsx:141-162`。这已经践行 Zed view 边界思想，后续应保留，不应笼统说我们的 React 每帧全量重算。Zed 对应隔离契约见 `.gpuix-main/zed/crates/gpui/src/view.rs:173-177`。
- **领域绘图已用平台能力。** lane 虚拟行与单一 retained hitbox 分离，证据 `apps/gpuix/src/project/sections/arrangement/lane/useLaneSurface.tsx:14-22`；quad-batch 映射 GPUI canvas，证据 `.gpuix-main/packages/native/src/quad_batch.rs:65-73,111-112`。无需把已有批量矩形重写成 Zed Rust 组件才能获得低层绘制。
- **性能 runner 对 React/native 双栈很有价值。** 上传字节量、桥接批次、React actual duration 是我们的特有成本，现有 runner 已观察它们，证据 `apps/gpuix/src/project/sections/arrangement/lane/verification/render-cost.tsx:79-82,225-263`。Zed profiler 强在原生帧链路，证据 `.gpuix-main/zed/crates/gpui/src/profiler.rs:785-870`；应该补齐关联，不是删除我们这一层。
- **输入框已经有共享外观与键盘边界。** 我们的 Input 统一 invalid/disabled、focus ring、文本快捷键传播及原生 input，证据 `apps/gpuix/src/ui/controls/Input/index.tsx:7-11,27-50,82-90`。Zed `ui_input::InputField` 统一 label、icon、mask、error 等更完整字段外壳，证据 `.gpuix-main/zed/crates/ui_input/src/input_field.rs:16-45`。有真实重复场景时可以补 field 组合，不必换掉原生输入。

## 不适用于我们

- **不能从 TS 直接用 Rust `Styled`、`Entity::cached`、`cx.notify` 或 `uniform_list` 闭包。** 它们属于 GPUI Rust 的 trait/entity/window 契约，证据 `.gpuix-main/zed/crates/gpui/src/styled.rs:22-24`、`view.rs:224-233`、`elements/uniform_list.rs:22-25`。我们经 React/native host 渲染，证据 `.gpuix-main/packages/native/src/renderer.rs:6030-6035,6098-6118`。可迁移的是 TS 组件边界、稳定 selector、已有 virtual-list/quad-batch；原生缓存须由 gpuix bridge 实现。
- **语法高亮、Git 状态和编辑器字体的完整主题模型不用照搬。** Zed 有 syntax font-style/font-weight 及 conflict/created/deleted 等角色，证据 `.gpuix-main/zed/crates/theme_settings/src/schema.rs:40-91`。我们实际已有电平、automation、clip ink 等 DAW 角色，证据 `apps/gpuix/src/shared/theme/colors.ts:64-78`。应补少量通用状态和音频状态，而不是添加没有消费者的 editor token。
- **Zed InputField 的 Editor 内核不能作为“应该接入完整代码编辑器”的理由。** 它包装 `Arc<dyn ErasedEditor>`，证据 `.gpuix-main/zed/crates/ui_input/src/input_field.rs:16-30`；我们已经通过 native `<input>` 使用文本能力，证据 `apps/gpuix/src/ui/controls/Input/index.tsx:54-71`。可借鉴字段外壳，不迁移 editor 依赖。
- **不照搬层级阴影。** Zed StyledExt 提供 elevation 系列，证据 `.gpuix-main/zed/crates/ui/src/traits/styled_ext.rs:49-93`；我们的视觉规范明确用颜色和细线表达工作站层级，证据 `apps/gpuix/src/shared/theme/README.md:99`。借鉴统一 surface 语义即可，差异不是缺陷。
- **不将整个 DAW 改成 rem 或普通一维列表。** Zed UI font size 影响 rem 和 UI 尺寸，证据 `.gpuix-main/zed/crates/theme_settings/src/settings.rs:40-45`；我们 lane 同时处理轨道 pinned 裁剪、横向 Clip 几何，证据 `apps/gpuix/src/project/sections/arrangement/lane/render-projection.ts:65-73,94-105`。音频工作区需要保留确定几何，只让合适的控件文字/密度可调。

## 辅助文档核实

通过 Context7 查询了 React 官方文档，确认 `memo` 不阻止其消费的 context 更新，局部 context 更新需要拆 consumer 与 memo child；`useSyncExternalStore` 需要在数据不变时复用 snapshot。来源 [React memo](https://react.dev/reference/react/memo)、[React useSyncExternalStore](https://react.dev/reference/react/useSyncExternalStore)。对应我们单一 ThemeContext 的证据是 `apps/gpuix/src/shared/theme/ThemeProvider.tsx:30,53-65,68-74`。主题切换通常本来就要更新大多数控件，所以不把这个合理的全局更新列为主要性能缺陷；优先处理高频交互与 scene 更新范围。

本报告没有执行或复核任何已有测试成绩。所有运行收益均需协调者后续实际验证。
