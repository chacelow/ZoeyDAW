# 输入、键盘、焦点与命令：我们和 Zed 的差距

## 结论与证据边界

最值得学的是把“命令是什么”“哪个上下文允许执行”“按键如何绑定”“处理后是否继续传播”分开。Zed 在焦点树上分派具名 action，我们主要在原始 keyDown 上手写分支，再依靠元素消费和窗口 owner 协作。Zed 的连接方式见 `.gpuix-main/zed/crates/gpui/src/key_dispatch.rs:1-45`；我们的连接方式见 `apps/gpuix/src/app/project/composition.ts:40-78`、`apps/gpuix/src/project/sections/arrangement/timeline/keyboard/controller.ts:79-180`。

本报告只读静态代码，没有运行测试、构建或真实桌面验收。Zed 指本仓库固定版本，不代表上游最新版本。路径均相对仓库根目录。

特别注意，2026-10-16 审查报告中的六项问题不能再直接当作当前未修复缺陷。此次读取时，保存已前移，三个控件已经消费按键，lane 已接失焦取消，多余的 Tab 入口已移除。下文把它们作为架构曾经漏掉的案例，而不是当前故障。历史来源见 `docs/reviews/2026-10-16-codebase/ui-platform-app.md:15-17`、`docs/reviews/2026-10-16-codebase/arrangement.md:16-18`；当前证据逐项列在后面的表里。

## 我们做得不差或更好

- 窗口 owner 的边界已经明确，WindowKeyboard 是每 render root 一个实例，subscriber 有 cleanup，后续订阅受 defaultPrevented 阻断。组合根 dispose 幂等并释放 lane/timeline，见 `apps/gpuix/src/platform/keyboard/index.ts:32-54`、`apps/gpuix/src/app/project/composition.ts:125-134`。这与 Zed 集中在一个 Window 焦点分派树上的方向一致，见 `.gpuix-main/zed/crates/gpui/src/key_dispatch.rs:69-90`。不应为了学 Zed 再增加第二个全局键盘 owner。
- Dialog 已有进入/返回焦点和应用作用域 Tab 环绕，不该把“我们没有 FocusHandle”夸大成“我们没有焦点恢复”。见 `apps/gpuix/src/app/dialog/ModalDialog.tsx:34-56`、`.gpuix-main/packages/react/src/components/dialog.tsx:171-194`、`.gpuix-main/packages/native/js/renderer-state.ts:242-270`。Zed ModalLayer 的额外优势是焦点包含关系判断，见 `.gpuix-main/zed/crates/workspace/src/modal_layer.rs:247-255`。
- 文本默认输入与快捷键阻断已作区别。stopTextShortcutPropagation 只停传播，不禁字符默认输入；Input 原生导航、撤销和提交的行为边界已有文档及真实 renderer 测试源码，见 `apps/gpuix/src/ui/controls/keyboard.ts:3-14`、`apps/gpuix/src/ui/controls/Input/README.md:7-10,25`、`apps/gpuix/src/ui/controls/Input/index.test.tsx:77-122`。Zed 也有 prefer_character_input 和 input handler 路径，见 `.gpuix-main/zed/crates/gpui/src/window.rs:5628-5645`。两者都不能将 preventDefault 与 stopPropagation 无条件合并到所有文本键。
- DAW 特有的 held B 临时绘制、noteOn/noteOff、电脑 MIDI 关闭和 editEpoch 变化时释放状态已有清晰 owner，见 `apps/gpuix/src/project/sections/arrangement/timeline/keyboard/controller.ts:51-76,96-106,183-221`。Zed 的示例是单次 Undo/Redo 与多键序列，见 `.gpuix-main/zed/crates/gpui/src/key_dispatch.rs:8-36,47-50`；这部分不是用 command palette 就能替代的逻辑。

## 不适用于我们

- 不能从 TS 直接调用 Rust 的 `FocusHandle`、`cx.bind_keys`、`.key_context`、`.on_action`。这些是 Zed 的 Rust render/API，见 `.gpuix-main/zed/crates/gpui/src/key_dispatch.rs:8-36`；我们消费的是 `@gpuix/react` 的 KeyEvent、renderer.focusElement 和 rootHandlers，见 `apps/gpuix/src/ui/controls/Menu/navigation.ts:1-13`、`apps/gpuix/src/platform/keyboard/index.ts:21-54`。应用和 renderer JS/types 两轮搜索未找到 KeyBinding/keyContext 等公开桥接，因此“不能直接套用”按当前可见 API 判断；应先做 TS 命令/绑定层，真正焦点树能力需 renderer 桥接，而非在应用重建 GPUI。
- 不照搬代码编辑器的 Editor/Pane、Vim 模态和多键 chord 全套语义。Zed 明确支持 `cmd-k left` 一类序列，见 `.gpuix-main/zed/crates/gpui/src/key_dispatch.rs:42-50`；我们的单键又承担持续发声与 held 绘制，见 `apps/gpuix/src/project/sections/arrangement/timeline/keyboard/controller.ts:96-106,139-161,183-201`。是否引入 chord 是产品选择，不能牺牲 noteOff 或增加演奏延迟。
- 不照搬“按钮 Space 默认激活”来追求通用控件一致。我们明确约定工具栏/Transport 按钮不吞 Space，播放由窗口 owner 执行；文本 Space 留在输入。见 `LESSONS.md:142-146`、`docs/architecture/gpuix-arrangement-composition.md:113-119`。迁移 Zed action 模型时，应把 Space 绑定为项目播放并保留文本上下文隔离，不能复制 Zed 的菜单/编辑器 Tab、Enter 绑定，见 `.gpuix-main/zed/assets/keymaps/default-macos.json:15-27,59-66`。

## 建议先做什么

先统一 command id 与 handled/pass 消费适配，再把已有窗口快捷键迁成声明表，让菜单展示读取真实绑定。第二步再做上下文注册与用户重绑定，命令面板复用同一表。域级焦点身份和失焦事件属于 renderer 边界能力，单独评估桥接，不在 TS 里再造原生焦点系统。这一顺序是建议，不是本次实现范围；成本判断均为 [INFERENCE]。
