# Import Auto-Warp: tempo and beat analysis options (2026-10-25)

**Scope:** research and an experiment specification; no dependencies or runtime changes made. A tempo estimate, a first beat, a bar downbeat, and a piecewise source-time ↔ musical-time warp map are _different_ outputs. None of the candidates below establishes Ableton Live-equivalent Auto-Warp or distinct effective stretch algorithms without integration and listening tests.

## Current path and why musical loops fail

- [`crates/engine/native/analysis/tempo_analysis.cpp`](../../crates/engine/native/analysis/tempo_analysis.cpp) opens a JUCE reader, rejects ACID one-shots, trusts a sensible ACID/`tempo`/`bpm`/`BPM`/`TBPM` metadata value first, and analyzes at most the first 60 s. The audible branch rejects audio shorter than 3 s, requires ≥6 detected onsets and a peak 10-ms-window mean-square energy ≥1e-8. It sends the **arithmetic mono average** to `tracktion::TempoDetect(1, rate)`. Its separate 10-ms energy onset picker requires an onset ≥8% of global peak, >2× the preceding 200-ms baseline and ≥150 ms after the previous onset. It uses median _successive onset_ interval as `pulseBpm`, adjusts the SoundTouch estimate toward that pulse by ×0.5/1/2 if within 8%, requires ≥80% successive intervals near 1–4 _integer_ beat periods within max(25 ms, 8%), and only replaces the detector's value with the exact median pulse for an entirely steady onset train. Thus a 1-bar 120 BPM 4/4 loop (2 s) is rejected before analysis; many two-bar sparse/syncopated patterns fail the onset-count and interval rules. Sixteenth-note subdivisions (< beat) fail the integer-period rule even for a perfectly regular loop. These are **code consequences, not measured corpus error rates**. Source: [analyzer](../../crates/engine/native/analysis/tempo_analysis.cpp).
- The detector's mono `(L+R)/channels` can cancel antiphase stereo; energy validation separately uses per-channel squared values, so detection and validation disagree about signal presence. Merely passing two channels to `TempoDetect` does not fix this: vendored SoundTouch `BPMDetect::decimate` also sums channel samples before enveloping. Compute phase-invariant per-channel onset/energy features or select the channel with most credible beat evidence, while retaining the original stereo signal for playback; do not average absolute samples into an audio track and claim that alone resolves BPM. Sources: [analyzer](../../crates/engine/native/analysis/tempo_analysis.cpp), [SoundTouch decimation](https://github.com/Tracktion/tracktion_engine/blob/877e39c0fe9f1c3e4a9d836f5f338688250875d7/modules/tracktion_engine/3rd_party/soundtouch/source/SoundTouch/BPMDetect.cpp).
- Tracktion [`TempoDetect`](https://github.com/Tracktion/tracktion_engine/blob/877e39c0fe9f1c3e4a9d836f5f338688250875d7/modules/tracktion_engine/timestretch/tracktion_TempoDetect.h) wraps SoundTouch `BPMDetect`; `processSection` interleaves input for it, `finishAndDetect()` obtains one BPM; no confidence, first-beat, downbeat, or marker map is returned through that wrapper. SoundTouch's [source](https://github.com/Tracktion/tracktion_engine/blob/877e39c0fe9f1c3e4a9d836f5f338688250875d7/modules/tracktion_engine/3rd_party/soundtouch/source/SoundTouch/BPMDetect.cpp) decimates, extracts an amplitude envelope and autocorrelates, then picks a peak; [header](https://github.com/Tracktion/tracktion_engine/blob/877e39c0fe9f1c3e4a9d836f5f338688250875d7/modules/tracktion_engine/3rd_party/soundtouch/include/BPMDetect.h) defines 45–190 BPM returned by the native detector (the wrapper's own `getSensibleRange()` is 29–200). SoundTouch does offer `getBeats(pos, strength)` with weak beat candidates, but Tracktion's wrapper doesn't expose it. The application's broad 30–300 BPM check does **not** expand the native detector's range; its pulse fallback can return beyond 45–190. The header comments about ~500 Hz are stale relative to implementation's 1000-Hz target; use implementation for operational claims. Sources: [vendored source](https://github.com/Tracktion/tracktion_engine/tree/877e39c0fe9f1c3e4a9d836f5f338688250875d7/modules/tracktion_engine/3rd_party/soundtouch), [Tracktion license](https://github.com/Tracktion/tracktion_engine/blob/877e39c0fe9f1c3e4a9d836f5f338688250875d7/LICENSE.md) (GPL-3.0-or-later or separate commercial), [SoundTouch file license](https://github.com/Tracktion/tracktion_engine/blob/877e39c0fe9f1c3e4a9d836f5f338688250875d7/modules/tracktion_engine/3rd_party/soundtouch/source/SoundTouch/BPMDetect.cpp) (LGPL-2.1-or-later); local pin [`scripts/audio/probes/tracktion/dependencies.lock.json`](../../scripts/audio/probes/tracktion/dependencies.lock.json) is `877e39c0fe9f1c3e4a9d836f5f338688250875d7`.
- Native FFI `zp_analyze_tempo` → [`crates/engine/src/analysis.rs`](../../crates/engine/src/analysis.rs) → [`src-tauri/src/playback/mod.rs`](../../src-tauri/src/playback/mod.rs) returns the current `{bpm: number|null, origin: metadata|analysis|unknown}` (wrapped in native response); [`crates/engine/Cargo.toml`](../../crates/engine/Cargo.toml) has no tempo crate. The existing native fixture tests 10-s 120 BPM impulses versus a 440-Hz continuous tone and decaying one-shot, plus ACID 123 BPM precedence; this does not establish syncopated, short, real musical, or antiphase accuracy. Source: [`playback_tests.cpp`](../../crates/engine/native/tests/playback_tests.cpp).

Measured separately by the parent using the current analyzer source linked into a standalone native probe: a regular 120-BPM 10-s pulse train returned 120; a 2-s loop and a syncopated 10-s pattern returned unknown; a regular antiphase stereo pulse train returned 120 through the energy fallback; a sustained tone and a one-shot returned unknown. Arithmetic stereo cancellation therefore affects the detector input, but did not make the regular antiphase case fail overall. These generated cases do not establish real-music accuracy.

## Narrow native experiment / acceptance contract (not performed)

1. Maintain metadata precedence and ACID `acidOneShot` exclusion. For audio, retain per-channel evidence until extracting phase-invariant attack/onset envelopes; do not allow stereo cancellation. For short clips, remove the unconditional 3-s and six-onset rejection **only after** loop-length/period hypotheses are checked against multiple repeats, interval regularity _and_ attack/noise evidence. If only a single unannotated beat or sustained periodic tone exists, return `unknown`, not a guessed BPM. Keep one-shot/tone/noise/ambiguous results nullable. This is a proposed experiment, not a verified threshold recipe.
2. Score candidate beat periods against onset positions **modulo a candidate period** (and, for a loop, modulo complete cycle), allowing offbeats, subdivisions, missing kicks and syncopation; do not demand that 80% of _adjacent_ attacks be integer beat lengths apart. Try candidates at `B`, `B/2`, `2B` only within explicit sensible musical prior/metadata/loop bar-count constraints. Separate `periodicityConfidence`, `metricalLevelAmbiguous` and `origin`; a strong sixteenth-note pulse alone doesn't tell quarter-note BPM. For 1-bar vs 2-bar interpretations at identical duration, absent meter or bar annotation, preserve ambiguity rather than silently choose. Compare SoundTouch raw result vs narrowly revised validation on the _same_ decoded PCM before introducing dependency.
3. For files longer than 60 s, sample multiple well-separated windows (including middle/end), don't infer a whole-song constant tempo from its first minute alone; quantify segment disagreement and keep `unknown` or `variable` when not constant. A global BPM doesn't determine an initial beat or the tempo changes needed for a variable warp-marker map. Explicitly test intros with silence, pickup and tempo ramps.
4. Record reference manifest: file SHA-256, legal provenance, rate/channel/duration, metadata trust, annotated BPM and permitted half/double alternatives, beat seconds, downbeat seconds **if annotated**, variable-tempo markers **if annotated**. Report coverage, exact BPM accuracy and octave-tolerant accuracy **separately**, false automatic-warp acceptance for one-shots/tones, and optional beat/downbeat timing errors. Report unknowns explicitly; never count a guessed downbeat as ground truth. Use held-out audio where any ML candidate could have seen training material.
5. Minimal generated corpus already exists locally: [`scripts/audio/generate-corpus.mjs`](../../scripts/audio/generate-corpus.mjs) emits deterministically seeded `CC0-1.0` 120-BPM click, seven-beat loop, leading silence, antiphase **tone** (not antiphase rhythmic track), one-shot, tone and 1-h sparse silent WAV; manifest marks musical quality unverified. Add deterministic 1/2/4-bar 120 BPM **musical** synthesized drum/syncopation variants with known beat/downbeat labels, antiphase rhythmic stereo, ghost notes, offbeats, pickups, noise and false-positive negatives in an isolated experiment (not as claimed current fixtures). For real loops, MTG's [Freesound Loop Dataset](https://mtg.github.io/mtg-toolbox/sample-packs/freesound-loop-dataset/) reports 9,455 Freesound loops, ~3,000 human-annotated and tempo labels, links [Zenodo](https://zenodo.org/records/3967852); its page states **CC BY-NC 4.0** and attribution. Use only for noncommercial evaluation after verifying each asset's actual license and the applicable dataset terms; don't ship any tracks as product fixtures. Author/user BPM labels are not beat/downbeat ground truth. For long musical files, use independently licensed own recordings with metronome/MIDI timing export or independently annotated, appropriately licensed held-out music; document provenance and don't assume the Freesound loops cover long variable-tempo music.
6. Compare the existing detector, postfilter-only prototype, aubio, `timestretch::analyze`, and Beat This! **only if** native fix fails predeclared cases and licenses/toolchains are acceptable; repeat across fixed 44.1/48-kHz mono/stereo sources and loop lengths. Expected outcomes: 120 BPM 2-s four-beat 4/4 click and syncopated variants return a candidate 120 only with defensible musical-period evidence; antiphase rhythmic stereo agrees with same source in phase; tone, one-shot, silence and sparse long silent file remain unknown; 60/120/240 ambiguity is reported, not hidden; variable 120→135 BPM does not assert a single sufficient warp map. These are **future expected outputs**, not test results or a claim every two-second loop can be inferred uniquely.

**Recommendation:** keep tempo analysis at the existing native import boundary and first benchmark a phase-safe, beat-grid-based replacement for the present rigid _validation_ and short-duration gate, while retaining nullable result and explicit ambiguity. Add another implementation only if held-out licensed musical corpus demonstrates a specific gap that cannot be fixed narrowly, with build/license/MSRV and quality measured independently. Do not wire a second audio playback engine or infer first beat/downbeat/variable warp markers from one BPM number.

## 2026-10-27 Metrical ambiguity guard

The current analyzer already accepts the existing short-loop and syncopated fixtures. This update addresses a narrower false acceptance. SoundTouch's periodicity estimate and the energy autocorrelation can agree on a repeated accent without identifying the musical beat unit. A synthesized accented triplet fixture returned 90.07 as `analysis` before the fix, despite also supporting a different straight subdivision.

The analyzer now checks selected onset phases with a fixed 64-bin circular histogram. A candidate with less than 80% straight-subdivision support but at least 80% triplet-subdivision support returns `unknown`. Tolerance includes the 10-ms energy-window resolution. Metadata still wins. The guard neither reads the filename nor converts the candidate to the file's labeled tempo, a half or double tempo, or a three-to-two alternative. It allocates no extra feature buffer and keeps the current SoundTouch detector and nullable response.

Unannotated swing and triplet performances can be conservatively rejected. UI import, save and undo acceptance remain separately tracked.

## 2026-10-27 Long-source consistency

The first-minute-only path accepted a synthesized 100-second WAV with 120 BPM for its first 60 seconds and 180 BPM thereafter as `{bpm:120, origin:"analysis"}`. The `--tempo` regression failed on that response before the change.

For sources longer than 60 seconds, analysis now runs the same detector sequentially over three 20-second windows at the beginning, center and end. Each window owns and releases its detector and feature buffers before the next. All three must return an analyzed BPM within 2% of the first window. Otherwise the existing nullable response is `unknown`, so import retains its original-speed path. There is no half/double-tempo normalization between regions. Metadata precedence and sources of at most 60 seconds retain their previous behavior.

The decoded-duration budget remains at most 60 seconds, though compressed-file seeking costs depend on the reader. Sampling can miss changes between windows, and a silent intro or outro can conservatively reject an otherwise steady song. This does not establish whole-song constancy, infer downbeats, produce Warp markers or implement a variable-tempo map. The deterministic native fixtures cover ending and middle tempo changes, steady long audio, unknown middle/end regions and authored metadata.

## 2026-10-27 Real-loop candidate comparison

An isolated `timestretch` 0.15.0 probe analyzed the decoded mono PCM without changing the playback backend. The existing native analyzer returned `unknown` for the user's 170 BPM-labeled melody and 140 BPM-labeled drum loop, and 95 BPM for the 95 BPM-labeled drum loop. The candidate returned approximately 85.42 BPM with confidence 0.50 for the melody, 140.03 with confidence 0.92 for the drum loop, and 95.02 with confidence 0.90 for the 95 BPM loop. The melody artifact also listed a 170.84 BPM candidate; this does not establish which metrical level is correct.

The existing synthetic accented-triplet negative returned 90.14 BPM with confidence 0.94 in the candidate. Confidence alone therefore cannot select a safe fallback: a threshold that accepts the 140 BPM loop would also accept this explicitly ambiguous negative. A continuous 440 Hz tone returned 0 BPM. The candidate's [documented API](https://docs.rs/timestretch/0.15.0/timestretch/fn.analyze.html) uses mono input, and its 1.85 MSRV exceeds the engine manifest's declared 1.77.2. It was not added to the application. A wider labeled corpus, phase-safe stereo analysis and a guard that preserves the triplet negative are required before integration.
